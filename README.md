# Управление задачами внутри события

## Состав проекта

- `db.py` — SQLite-соединение и схема БД.
- `auth.py` — пользовательская сессия и проверки ролей/доступа.
- `event_service.py` — доступ к событиям, состав команды и участники события.
- `task_service.py` — бизнес-логика задач и комментариев.
- `ui/main_window.py` — окно списка задач.
- `ui/create_task_dialog.py` — создание задачи.
- `ui/comments_dialog.py` — история и отправка комментариев.
- `ui/assign_dialog.py` — назначение исполнителя тимлидом.
- `ui/task_card.py` — карточка задачи.
- `main.py` — точка входа и демонстрационные данные.

## Запуск

Python 3.10+:

```bash
python -m pip install -r requirements.txt
python main.py
```

По умолчанию база `tasks_app.db` создаётся рядом с `main.py`. При первом запуске создаются демонстрационные пользователи, команда и событие. Демонстрационный вход — пользователь `lead` (тимлид). Для проверки роли участника измените `DEMO_USER_ID` в `main.py` на `2`.

## Форматы даты и времени

Вводите дедлайн и напоминание в формате `YYYY-MM-DD HH:MM`, например `2026-11-02 18:30`.
Поле напоминания необязательно. Пустое поле сохраняется как SQL `NULL`.

## Важные решения

- Вся бизнес-логика и проверки прав находятся в `task_service.py`, а не в интерфейсе.
- Участник автоматически становится исполнителем своей задачи; переданное UI значение исполнителя не даёт участнику назначить другого пользователя.
- Назначать исполнителя может только тимлид команды, связанной с событием.
- Комментарии доступны только пользователям, имеющим доступ к событию.
- Для доступа используются `event_members` и `team_members`; это минимальная схема, которую можно встроить в существующую БД.
- `change_task_status` разрешает менять статус исполнителю, создателю задачи или тимлиду соответствующей команды.
- SQLite хранит даты как строки ISO-подобного формата `YYYY-MM-DD HH:MM`. В реальном приложении при переходе на PostgreSQL слой подключения можно заменить.
